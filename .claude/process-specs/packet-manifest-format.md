# The packet manifest format (`packet-manifest/1`)

**Status:** the format ADR-049 §7 calls for — the single source for the shape of the
implementor-packet files. The producing/consuming tooling is the `theagent2 workspace`
subcommand family (`@theagent2/runtime`, ADR-049 §10). Concrete manifests live in the
**project** repository (`packets/` at the project root), never in theagent2 and
never inside a workspace's rw surface.

## Purpose

One allowlist per implementor packet — the enumeration of everything a materialized workspace
(ADR-049) contains, and the audit proof of what the implementor could have seen. Consumed by:

1. **`workspace materialize`** — builds the workspace from it (`git archive <sha> -- <paths>`),
   derives the srt read-only mount set, writes the workspace receipt;
2. **`workspace lint`** — the fail-closed repo check (ADR-049 invariant 4), wired into
   `just test`;
3. **`workspace preflight`** — the implementor's own refusal check, in two phases (#694):
   at launch the receipt is present and history is the provenance commit alone (depth 1);
   on every later invocation that commit is still the root of a linear history and the tree
   is clean (*baseline + N commits on top*);
4. **Gate-4 acceptance / audit** — "could the implementor have known X?" is answered by
   reading the run record, not by trusting a session log.

## The file family

| File | Authorship | Lives in | Role |
| --- | --- | --- | --- |
| `packets/<component>.packet.yaml` | **generated** (never hand-edited) | project repo | the recipe: rw/ro/docs allowlist |
| `packets/<component>.extras.yaml` | hand-written (SA), **normally absent** | project repo | deliberate doc additions only |
| `packets/extras.json` | hand-written (SA) | project repo | the **derive input**: the doc set + the non-scaffolded packets |
| `packets/hidden-roots.yaml` | hand-written (spec owner) | project repo | declared hidden-partition roots the lint guards |
| `packets/runs/<component>/<sha7>-r<N>.json` | emitted by `materialize` | project repo | the run record: resolved snapshot per materialization |
| `packets/runs/<component>/<sha7>-r<N>.report.md` | **transcribed by the conductor** | project repo | the implementor's FINAL MESSAGE, verbatim — it cannot write the file itself (#553, #1654) |
| `packets/runs/<component>/<sha7>-r<N>.audit.md` | **transcribed by the conductor** | project repo | the conformance auditor's final message — the auditor is read-only |
| `packets/runs/<component>/<sha7>-r<N>.craft.md` | **transcribed by the conductor** | project repo | the craft reviewer's final message — it has no `Write` tool by design |
| `.packet/manifest.json` | emitted by `materialize` | workspace (provenance commit) | the receipt: byte-identical copy of the run record |
| `.packet/tool/theagent2` | emitted by `materialize` | workspace (provenance commit) | the shim on the pinned runtime, first on the workspace `PATH` (#696) |
| `.theagent-run/skills-loaded` | appended by the PostToolUse hook | workspace (gitignored scratch) | which lazy skills this session has loaded, for the gate below (#896) |

No human reviews the generated recipe (ADR-049 §4): the composition is mechanical on the
ADR-022 Interface/Service cut, and the withholding guarantee is the lint, not eyes. The extras
overlay is an action the Software Architect takes, not an artifact anyone reviews.

## The recipe (`packets/<component>.packet.yaml`)

```yaml
format: packet-manifest/1
generated: "GENERATED by `theagent2 workspace materialize --derive` from widgets.method@<rev> — DO NOT EDIT (ADR-049 §4)"
component: Manager/Order            # model component id (Concept/Name)
role: implementor-csharp            # selects the packet template (rw/ro shape)
allowlist_version: 1                # bumped by the generator when the derived path set changes

# The ONLY rw surface: the component's own Service project (ADR-049 §3).
rw:
  - Widgets/Component/Manager/Order/Service/

# Everything else present, read-only. Enumerated explicitly by the generator —
# no globs anywhere in this file.
ro:
  - Widgets/Component/Manager/Order/Interface/
  - Widgets/Component/Manager/Shipping/Interface/      # ALL Interface projects …
  - Widgets/Component/Access/Order/Interface/          # … foreign Service projects are ABSENT
  - Widgets/iFX/
  - Widgets/Directory.Build.props
  - Widgets/analyzers/
  - Widgets/Spec/Widgets.Spec/                         # whole visible partition (ADR-049 Q8)
  - Widgets/Spec/Widgets.Spec.Composition/             # simulators
  - Widgets/Spec/runner/

# The named doc set — individual files, never a folder (ADR-049 §4).
docs:
  - docs/03_Design/FAULT-CATALOG.md                    # the checked line that resolves F4
  - docs/03_Design/DEPLOYMENT-VIEW.md
```

Semantics:

- **Paths are repo-relative, `/`-separated; a trailing `/` marks a directory prefix** (the
  whole subtree at the baseline), no trailing `/` marks a single file. These are the only two
  forms — no globs, no negations, no excludes. Absence is the default; there is nothing to
  subtract from.
- **Mono-repo wiring (#479, 2026-08-11):** "repo" is the REAL git repository — which may be a
  mono-repo holding the project as one subdirectory — not the project subdirectory itself. The packets
  directory keeps living in the project (its own `packets/` directory) and every tool takes it
  as `--packets <repo-relative dir>`; allowlist paths anchor at the git root so a packet can carry
  the theagent2 toolchain the generated skeleton references by relative path (conformance
  analyzers, SoEx iFX, spec runner) — enumerated dirs, never a package root (the spec package
  root would drag the runner's own hidden fixture partition in). Recipes are generated by
  `theagent2 workspace derive` from the method store + the `implementor-csharp` template.
- **`rw` ∪ `ro` ∪ `docs` is the complete workspace.** Anything not listed does not exist in
  the workspace — not "is not mounted": *does not exist* (ADR-049 §2 step 2).
- `rw` entries must be disjoint from `ro`/`docs`; across packets, `rw` sets are disjoint by
  the ADR-022 cut (one packet's rw = its own `Service` project).
- `role` names the generator template; `allowlist_version` is monotonic per packet and cited
  by the provenance commit ("materialized from `<sha>`, allowlist v*N*").

## The extras overlay (`packets/<component>.extras.yaml`)

```yaml
format: packet-extras/1
component: Manager/Order
docs:
  - docs/02_Business/BP01_TakePhoneOrder.md   # individually named files only
    # rationale is mandatory — an extras entry is a recorded deliberate decision
rationale:
  "docs/02_Business/BP01_TakePhoneOrder.md": "DesignGap DG-012: spec silent on phone-order wording; SA approved 2026-08-XX"
```

Only `docs` may be extended — never `rw`, never `ro` code paths. Normally the file does not
exist; its presence is itself the record that a deliberate addition was made. Each entry
carries a `rationale` line (same regime as the seqmap feasibility sidecar: provenance
mandatory).

## The derive input (`packets/extras.json`)

Everything `workspace derive` needs that the model does not carry, DECLARED in one versioned
file rather than typed per invocation:

```jsonc
{
  "docs": [                                     // the doc set EVERY component packet carries
    "docs/03_Technology/03_Deployment/01_Deployment-View.md",
    "docs/03_Technology/03_Deployment/03_Product-Fault-Taxonomy.md"
  ],
  "stations": [ /* Client packets: id, dir, rw, contracts, ro, docs, skills */ ],
  "componentSkills": {                          // per COMPONENT packet, only where the tier
    "Utility/ConfigurationUtility": [           // selects no conventions of its own (#623)
      "idesign-knowledge"
    ]
  },
  "driverRo": {                                 // per DRIVER packet, only where a driver check
    "Access/Channel/woocommerce": [             // needs its visible spec host in the workspace
      "csharp/Spec/Figaro.SpecLayer.Access.Channel.Store.WooCommerce/",
      "experiments/woocommerce/src/WooSimulator/"
    ]
  }
}                                               // NO "stores": driver packets are DERIVED (#1099)
```

- **`docs` is required and non-empty**, and each entry names one file (a trailing `/` is
  refused — the doc set never carries a folder). `stations` are the non-scaffolded packets that
  still have to be declared (Clients are not a scaffolded layer, ADR-027); each declares its own
  doc set, and a station must declare its `skills` (#623). Any other key is ignored, which is how
  the file carries its own rationale (`_comment`, `_design_owned_seams`) — so a misspelt `docs`
  reads as no declaration at all, and `derive` refuses rather than deriving a doc-less packet.

### `componentSkills` — a component packet's declared skill set (#623)

`materialize` selects a packet's skills by TIER (`csharp-<tier>-*`) and **refuses** a packet that
selects nothing and declares nothing: silence is refused rather than defaulted, because the
failure mode of a default is a workspace that LOOKS correctly provisioned. For one class of
packet that refusal was unsatisfiable — a **library Utility** (ADR-074) stands on no slot, so it
is not treated as an Access, and no `csharp-utility-*` skill exists for its tier to select. Its
packet is generated and stamped `DO NOT EDIT`; a hand-added `skills:` line is a meaningful line
to `--check`, so the packet reads STALE and the next `derive` deletes it.

So a component packet declares its skills the same way a station does, in this file:

| | |
|---|---|
| key | the packet's component id in SLASH form (`Utility/ConfigurationUtility`) — the same id the slot table and `stations` use |
| value | a **non-empty** list of skill names. An empty list is not "nothing declared"; it is a packet that would be refused at materialize time with nothing left to correct it by |
| when to write one | only where the tier selects nothing of its own. A tier that already selects its conventions is provisioned; declaring them again gives one fact two originals |
| what `derive` emits | the same `skills:` block, with the same `DECLARED, never defaulted` comment, that a station packet carries. Omitted entirely for a component with no declaration, so every packet that needs none is byte-identical to what it is today |

`derive` **refuses the whole run**, writing nothing, when a key names no component packet it
writes: a declaration that provisions nothing is a declaration somebody believes is working —
the same shape as the #1629 `ro` line that named no file. **The `materialize` refusal itself is
unchanged**, which is the point of the route: "declared, never defaulted" is exactly the property
it was built to protect.

### `driverRo` — a driver packet's declared read-only extension

A driver packet's `ro:` is derived from four sources: the Resource project holding its seam, the
root build files, the project's `iFX/` and the toolchain. A **driver-level check** needs more in
the driver's workspace — the VISIBLE spec host that checks that driver, and the simulator the host
drives. Which host checks which driver is a design fact that neither the model nor the slot table
carries, so it is declared here, once, like `stations` and `spec`.

| | |
|---|---|
| key | a **driver** packet's id in SLASH form, exactly as derived from the deployment view's slot table: `Access/<Stem>/<slot>` (or `Utility/<Name>/<slot>`) |
| value | a **non-empty** list of **REPO-relative** paths — files, or folders with a trailing `/` |
| what `derive` emits | the declared paths appended to THAT packet's `ro:`, after the derived lines, in declaration order, each once (a line the packet already derives is not repeated). No other packet gets them. A packet with no key is byte-identical to one derived before the key existed |
| effect | the extended packet's path set changes, so its `allowlist_version` moves by one on the next derive — an effect, never a thing you write |

**Paths are repo-relative, not C#-root-relative** — the one difference from `spec` and a station's
`ro`. It is forced: a driver's simulator lives wherever the project keeps its experiments, which
need not be under the C# root (figaro: `experiments/woocommerce/src/WooSimulator/`).

`derive` **refuses the whole run**, writing nothing, when:

- **a path reaches a hidden partition** — it is under or equal to a root declared in
  `packets/hidden-roots.yaml`, it is a folder that **contains** such a root (materializing the
  parent would export the partition), or one of its segments carries the declared hidden naming
  suffix (`.Hidden`). The message names the path and the root. This is enforced at DERIVE time,
  not left to `lint` and `materialize` (ADR-013, ADR-049). A project with **no**
  `hidden-roots.yaml` cannot use the key at all: the refusal cannot be judged without the
  declaration, and `materialize` would refuse the packet anyway (fail closed);
- **a path does not exist** — the `spec` key's rule: `materialize` resolves every allowlisted
  path against the git index, so a line naming nothing refuses the workspace rather than thinning
  it. The consequence for ordering: the declaration is written **after** the host it names exists;
- a path is empty, padded, absolute, a traversal (`..`/`.`) or a glob; a folder is named without
  its trailing `/` or a file with one (lint rule 3); or a path overlaps the driver's own `rw`
  project (rw and ro must be disjoint, ADR-049 §3);
- **a key names a packet this derive does not write as a driver packet** — an unknown id, or the
  id of a component or station packet. Fail closed, for `componentSkills`' reason: a declaration
  that mounts nothing is one somebody believes is working, and here that is a driver check whose
  host is silently absent from the workspace. The extension is for driver packets only — there is
  no `rw` extension, no component-packet extension and no glob;
- a value is an empty list, or not a list of strings.

### A station packet (#1629)

| field | meaning |
|---|---|
| `id` | the packet's component id, SLASH-FORM (`Client/Counter`) — the first segment selects the launch surface's tier skills |
| `dir` | csharpRoot-relative station project directory |
| `rw` | csharpRoot-relative directories the station writes — its markup and scoped stylesheets, never its own `Anchors/` or csproj |
| `contracts` | csharpRoot-relative Interface projects it may call (Manager contracts only) |
| `ro` | csharpRoot-relative **sources it compiles against and does not own** — files, or folders with a trailing `/`. Optional |
| `docs` | repo-relative doc lines, individual files |
| `skills` | required and non-empty (#623) |

The packet's `ro:` list is then, in this order: the station's `Anchors/` and its csproj, the
declared `contracts`, the declared `ro`, the build files **from the C# root down to the station**,
the project's `iFX/` and the toolchain set — de-duplicated, so a line that is both declared and
derived is mounted once.

- **`ro` is for the SHARED UI of a station project group.** Several stations compile into one Razor
  assembly and share `Components/_Imports.razor`, `Components/Layout/`, `Localization/` and
  `wwwroot/`; a screen does not compile without `_Imports.razor` and the localization types. Nothing
  in the tree distinguishes those from a sibling station's private markup, so they are declared —
  the same reason `stations` and `spec` are declared at all. Until #1629 there was no field for
  them, and figaro listed all 25 tracked files of `csharp/Client/` — fonts included — as `docs`
  lines, which works (a `docs` line is materialized exactly like an `ro` one) and is wrong three
  ways: build inputs labelled documentation, no folder can be named, and every new shared file has
  to be added to every station by hand.
- **The build files are DERIVED, not declared.** `derive` mounts every `Directory.Build.props` /
  `Directory.Build.targets` it finds in each directory from the first segment under the C# root
  down to `dir` **itself**, exactly as it already does for the C# root. MSBuild walks up from the
  project directory, so a build file on that path applies whether or not the packet names it — and
  when the workspace does not carry it, MSBuild keeps walking and finds the C# root's instead, so
  the rules in the skipped file **silently do not attach**. Measured with `dotnet msbuild -pp` on an
  exported figaro VW02 station: 2 FIGARO targets (FIGARO001 — a Client's resolved reference closure
  is Manager contracts only; FIGARO002 — no source under `experiments/`) with
  `csharp/Client/Directory.Build.targets` present, 0 without it, **no error either way**. The walk
  stops at the C# root: the root's own two files are already mounted, and no packet anchors source
  above it.
- **Every `ro` line is checked where a human edits it.** `derive` refuses — writing nothing — a line
  that is empty, padded, absolute, a `..` traversal, names a path that does not exist, spells a
  folder without its trailing `/` (or a file with one), or overlaps the station's own `rw`. Each of
  those is a defect that otherwise surfaces at lint (rule 3, which applies to the new lines
  unchanged) or at `materialize`, which resolves the whole allowlist against the git index and
  refuses the entire workspace rather than mounting it thin.
- **`Anchors/` is mounted when the station has one.** The line used to be unconditional, so a Client
  with **no screens** could not be a station at all: lint rule 3 and `materialize` both require
  every allowlisted path to exist, and git cannot track an empty directory — the "commit an empty
  `Anchors/` marker" workaround yields a path that is on disk and absent from the git index. It is
  now omitted when the directory is absent or empty, and the station is **named in the derive
  output** (`no anchors: <id>: …`): a screen-bearing station whose anchors were never generated is a
  real mistake, and silence is what made #1629's other half invisible.
- **Migration.** Moving a project's station lines out of `docs` into `ro` shrinks the doc set, so
  the first derive after this change needs `--drop-docs` once (#621).
- **A driver packet is DERIVED WHOLE, one per SLOT (#1099).** `stores` used to be declared here,
  listing an id, a directory, a seam and a doc set per driver. It is gone: `deployment-view.yaml`'s
  slot table states every one of those and is reviewed at the Blueprint gate, and ADR-049 §4
  prefers derived over authored precisely so a second original cannot drift from the first. The
  drift an authored list produces is not symmetric, which is why it was removed rather than
  validated: a slot missing from the list is a driver project nobody can be dispatched to, and it
  fails SILENTLY — the manifest is complete on its own terms, so no check has anything to compare
  it against. A derived list cannot be short, because the slot table it is derived from is what
  defines the set.

  `derive` emits one packet per slot that names a `driverProject`:

  | field | from |
  |---|---|
  | `component:` | `Access/<Stem>/<slot>` — e.g. `Access/Catalog/catalog-store` |
  | `rw:` | the slot's `driverProject`, and nothing else |
  | `ro:` | the Access's `Resource/` project (the seam and its generated slot carrier), the build props, the project's `iFX/`, the toolchain set |
  | `docs:` | the declared `docs` set, plus `02_Store-Seam-Interfaces.md`, plus **this slot's** `protocol/<seam>.protocol.yaml` and `schema/<seam>.schema.sql` |

  **One packet, one slot, one product, one flavor skill.** An Access standing on a relational store
  *and* a REST API becomes two driver packets, each carrying one flavor skill — which is what #456
  demanded and what one packet per Access could not deliver. The sheets and schemas are keyed by
  **seam** (#1090), and a packet carries only its own: the right protocol sitting beside a wrong one
  with nothing saying which is the #456 defect in document form.

  The **slot name**, not the id, is what everything keys on. It is unique system-wide by
  construction (ADR-065 decision 2), so `materialize` looks a driver's flavor up by slot name across
  the whole table. Nothing parses the packet id for meaning any more — the old two-segment form
  (`Access/Catalog-Store-Sqlite`) had two files independently taking the text before the first dash,
  which could not tell two slots of one Access apart.

  A slot with **no `driverProject`** is skipped rather than refused: a resource-designer pass names
  slots before anybody creates the projects, and a derive that failed there would block a project
  for having designed ahead of construction. Each doc line is added only when the file is on disk (a
  driver packet can predate its project's sheets, and a doc line pointing at nothing would make
  `materialize` refuse the workspace) and never twice. A sheet appearing makes the packet stale,
  which is the right direction: the implementor's doc set changed.

  **Renaming a packet orphans its run records.** They live at `packets/runs/<slug>/`, keyed by the
  slugified id, and nothing cross-checks that directory against any packet — so the ADR-057 §2a
  from-empty-rebuild history silently stops attaching and the ordinal restarts at `r1`. Move the
  directory in the same change.

- **Why the doc set lives here and not on the command line (#621):** regeneration is a
  **REPLACE** of each packet's doc set, not a merge into it. When the set was a `--docs` flag,
  one invocation that named one path where the packets carried two removed the product fault
  taxonomy from **all nine** of the project's component packets at once, bumped
  `allowlist_version` on each, and printed `written: …` for every one. Nothing failed — a missing doc breaks no build;
  it only stops the next implementor ever seeing which error codes exist.
- **`derive --check` is the staleness gate (#866).** It plans every packet, writes nothing —
  not even the packets directory — and exits non-zero while any committed recipe differs from
  what the generator produces now, naming each packet, each moved line and each
  `allowlist_version` bump. Wired into `just test` as `just derive-check`, the same shape as
  `theagent2 sync --check` and `bpmn-dsl build --check`. Why it exists: the recipe is *derived,
  never authored*, and a generator change nobody re-derived leaves the two silently disagreeing.
  #793 added the conformance package's `Directory.Build.props` to derive's toolchain set without
  a re-derive, so for three commits all 15 committed packets were one `ro:` line behind — and
  every workspace materialized from them was missing the very file that keeps the SourceLink git
  query off (#579). Nothing failed here, because a missing read-only path breaks no build in this
  tree; it breaks the workspace over there. Exit codes: `1` = stale (a report about the tree),
  `3` = the invocation or the inputs are wrong, as everywhere else in this command.
- **`derive` refuses a doc-set shrink.** If regeneration would remove any doc line a packet on
  disk carries, the whole run is refused — it names every packet and every dropped line and
  **writes nothing**, so the packets never half-agree. `--drop-docs` authorizes the removal when
  it is intended; the destructive act is the one you have to ask for.

## The hidden-roots declaration (`packets/hidden-roots.yaml`)

```yaml
format: packet-hidden-roots/1
roots:
  - Widgets/Spec/Widgets.Spec.Hidden/
naming: ".Hidden"   # normative suffix convention (ADR-034 §9) — lint cross-checks it
```

The explicit, lint-guarded statement of what must never be allowlisted. Knowing the *name* of
a hidden root is harness/spec-owner information; the file itself is never in any packet, and
no packet may list any path under a declared root.

## The run record and the receipt

`materialize` resolves recipe + overlay at a baseline and emits the run record —
committed to the project repo at `packets/runs/<component>/<sha7>-r<N>.json` (`<sha7>` =
short baseline SHA, `r<N>` = per-baseline ordinal, one higher than the highest RUN RECORD
already there — the companion `.report.md` / `.audit.md` / `.craft.md` files share the round's
name and are not rounds; no wall-clock timestamps, same determinism regime as
`seqmap-format.md`) — and writes the **receipt** to
`.packet/manifest.json` inside the workspace, included in the provenance commit and outside
every rw path (land-back never picks it up). The receipt is identical to the run record
except `workspace.provenance_commit`, which is `null` in the receipt — the provenance commit
cannot contain its own hash; only the run record, written after the commit, carries it.

```jsonc
{
  "format": "packet-manifest-run/1",
  "component": "Manager/Order",
  "role": "implementor-csharp",
  "packet": "packets/Manager-Order.packet.yaml",
  "extras": null,                              // or the overlay path, if one existed
  "allowlist_version": 1,
  "baseline": {
    "sha": "<40-hex>",                         // the explicit per-run decision (ADR-049 §6)
    "mode": "continue-from-current",           // | "regenerate-from-skeleton"
    "rebuild_approval": null                   // the recorded approval of a from-empty rebuild (#980)
  },
  "paths": [                                   // the resolved allowlist, one entry per recipe line
    { "path": "Widgets/Component/Manager/Order/Service/", "mode": "rw", "sha256": "<tree hash>" },
    { "path": "docs/03_Design/FAULT-CATALOG.md",          "mode": "ro", "sha256": "<blob hash>" }
  ],
  "tool": {                                    // the pinned theagent2 the workspace ships (#696)
    "entry": "/abs/path/to/theagent2/packages/runtime/dist/index.js",
    "node":  "/abs/path/to/node",
    "sha256": "<hash of entry at materialize time>",
    "shim":  ".packet/tool/theagent2"
  },
  "skills": {                                  // the resolved skill set, split by delivery (#896)
    "provisioned": ["idesign-knowledge", "ui-ux-pro-max"],   // everything the packet resolves to
    "external":    ["ui-ux-pro-max"]           // installed plugins: declared, not copied, must be loaded
  },
  "workspace": { "provenance_commit": "<sha of the workspace's single initial commit>" }
}
```

### `baseline.rebuild_approval` — who authorized the rebuild (#980)

`continue-from-current` — the implementor edits the code already there — is the default, needs
nobody's approval, and records `"rebuild_approval": null`. `regenerate-from-skeleton` — the
component is rebuilt from an **empty directory** — is the exception and always needs the Software
Architect's approval (ADR-057 §2a, ADR-049 §6, his ruling 2026-08-23 #942), so its record carries
a **reference to where that approval is recorded**: an issue comment URL, an issue number, a
ruling id, the run-log line. "Who authorized this rebuild" is then answered by reading the
manifest, the same standard §7 sets for everything else in it.

- **`materialize` refuses** `--mode regenerate-from-skeleton` without `--rebuild-approval <ref>`,
  before anything is exported — a refused launch leaves an empty disk. It also refuses
  `--rebuild-approval` **with** `continue-from-current`: that would file his answer against a
  rebuild nobody did.
- **What is checked is presence, not authenticity** (SA decision). The reference must exist and be
  followable — non-blank, one line, long enough to lead somewhere — and nothing verifies that the
  approval is genuine: no network call, no `gh`, no authorship check. The failure being prevented
  is a session *forgetting to ask*, not a session lying.
- **`"pre-rule"`** is the one reserved value: a run recorded before the rule existed. It is not an
  approval — `materialize` refuses it on the command line — and `workspace lint` names every
  record carrying it in its output rather than passing it in silence.

`sha256` values hash the exported content (per file; directories hash their sorted file-hash
list, skipping build outputs: `bin/`, `obj/`, `TestResults/`, `node_modules/`, `dist/` —
ADR-050 Q2), so the receipt proves not only *which* paths but *which bytes* the implementor
could have seen.

## The tool surface (#696)

`materialize` prints — and the agent def it provisions says — that the implementor's first act is
`theagent2 workspace preflight`. So the workspace ships that command:

- **`.packet/tool/theagent2`** — a `sh` shim exec'ing ONE pinned runtime: the `dist/index.js` of
  the runtime that materialized this workspace, with the node binary it ran under, both recorded
  in the receipt's `tool` block with the entry's sha256. Not a `PATH` lookup and not a build
  output an implementor found: "which `theagent2` did this run use" is answered by the receipt.
- **`.claude/settings.json` → `env.PATH`** — that directory first, then the host `PATH`, written
  as a literal absolute list. Claude Code sets `env` values verbatim and does **not** expand
  `${PATH}`, so an interpolated value would hand the session one directory and no `git`/`dotnet`.

It is `.packet/tool/`, not `.packet/bin/`: the generated `.gitignore` (#581) ignores every `bin/`
as build output, which would keep the shim out of the provenance commit. `.packet/` is Edit-denied
by the L2 ladder, so the implementor can run the shim and cannot rewrite it.

Why it is not cosmetic: before this, `theagent2` was on no `PATH` inside a workspace, and
`command not found` reads to an agent like a refusal — so an implementor either stops when it
should work, or (as one Stage-E implementor did) reaches an absolute path into the real repository
from inside a workspace whose brief says no path outside it exists.

## The lazy-skill gate (#896)

A packet's skills reach the implementor two different ways, and only one of them is delivery:

- a **bundled** skill is copied into `.claude/skills/<name>/` and its `SKILL.md` is inlined into
  the workspace's agent def (#895) — the rules are in front of the implementor whether or not it
  invokes anything;
- an **external** skill is a user-level plugin (`ui-ux-pro-max`, the station packets' presentation
  bar). It lives in the user's plugin install, cannot be copied into a workspace, and reaches the
  implementor **only** if the implementor calls the `Skill` tool.

For the second kind the agent def's "load every skill below" line is an instruction and nothing
more — the same shape as the presentation bar that reached the implementor only when a conductor
remembered to type it into the kickoff (#623). So `materialize` arms a gate:

- the receipt's `skills.external` says which skills the session owes;
- a **PreToolUse** hook — wired **only** when that list is non-empty, so a packet with no lazy
  skills pays no subprocess per tool call — refuses the **first `Write`/`Edit` into an `rw` path**
  until every one of them has been loaded. Reads, `Bash`, preflight, planning and `REPORT.md` are
  untouched: the gate fires late enough not to obstruct understanding, early enough that no line
  of code is written without the rules that govern how it is written.

Evidence is positive and two-channel, never ambient: the **PostToolUse** hook appends each
completed `Skill` call to `.theagent-run/skills-loaded` (gitignored scratch — it can never dirty
`preflight` or `land`), and the session **transcript** is scanned for `Skill` tool calls whose
result was not an error, so a resumed session is not asked to load what it already loaded. No
evidence at all is a block, not a pass — absence of evidence is exactly how the failure mode
presents.

The block names the missing skill, prints the exact `Skill(skill: "<name>")` call that clears it,
and states that the workspace is intact and writable. A bare refusal reads to an agent as an
environment fault, and an agent that reads it that way either stops when it should work or works
around the guard (#553).

## In-box enforcement (ADR-050)

Alongside the receipt, `materialize` arms the in-box read-only ladder: write bits stripped on
every ro/docs **file** (directories stay writable for build outputs), and a
`.claude/settings.json` in the workspace denying `Edit`/`Write` on every ro path and
`.packet/`. `land` is the tamper gate: it **recomputes the ro hashes against the receipt and
refuses to land** — naming the changed paths — if any ro content differs, whatever the
mechanism. Binding rule (ADR-050 L4): **no gate ever runs specs from workspace state** —
visible-spec green and acceptance always run against the real repository's spec after
land-back. Kernel enforcement (srt / `:ro` mounts) is optional depth where the launch host
provides it (#479), not a prerequisite.

## Coordinated land-back (`land --group` — ADR-049 §8b, #853)

A contract change spanning components goes architect-first, then one materialized dispatch
per affected component (invariant 5); the repairs land as **one commit, proven green before
it exists**, never as N sequential land-backs with the repository red in between:

```
theagent2 workspace land --repo <dir> --task <id> --group <ws1> <ws2> … --verify '<build command>'
```

Members must be **siblings off one baseline** (equal `baseline.sha` in every receipt —
materialize each with the same explicit `--baseline <sha>`), with disjoint `rw` surfaces
(the ADR-049 Q6 guarantee that makes the combined diff conflict-free). Every member passes
the same per-workspace gates as a single land (receipt, L3 tamper hashes, dirty-rw). The
combined diff is applied to a **scratch worktree of the target's HEAD** — committed state
plus the member diffs, exactly the tree the commit would produce — and the `--verify`
command runs there. Red, or any member tampered/empty/off-baseline, refuses the **whole
set** with the real tree untouched (§8a: refuse, don't thin — never land the subset that
happens to compile). Green lands one atomic `git apply --index` + commit whose body answers
"were these landed together?": the task, the shared `Group-Baseline`, one `Member:` line
per workspace (component + provenance commit), and the `Verified:` command.

## Lint rules (`workspace lint` — fail-closed, part of `just test`)

1. No recipe or extras path lies under a declared hidden root, and no allowlisted path
   matches the `naming` suffix. A directory in the repo matching the suffix that is *not*
   declared in `hidden-roots.yaml` also fails (sync check — the declaration may lag, the
   lint may not).
2. No visible `.csproj` inside any allowlisted path references a hidden assembly
   (project reference or package reference by hidden name).
3. Every recipe/extras path exists at the baseline SHA being materialized (a stale allowlist
   fails loudly *before* launch, not as a silently thinner workspace).
4. Extras entries are individual files with a non-empty `rationale`; extras never touch
   `rw`/`ro`.
5. Recipe files carry the generated header and match a fresh derivation from the model
   (staleness guard, same pattern as `seqmap check`).
6. Strict YAML subset, unknown keys fail — same regime as `si-binding-format.md`.
7. Every run record under `packets/runs/` parses, is a `packet-manifest-run/1`, and answers the
   rebuild question (#980): `baseline.mode: regenerate-from-skeleton` with no
   `baseline.rebuild_approval` fails, and so does an approval recorded against
   `continue-from-current`. `workspace lint` is part of `just test`, so a record claiming an
   unapproved rebuild goes red at every landing, not only at the launch nobody watched — and a
   hand-written one, the only way such a record can now come to exist, fails the same way.

## Semantics and guarantees

- **Allowlist, never blocklist** (ADR-049 §4): the failure mode of a stale manifest is a
  *missing* file — loud, the implementor blocks — never a leaked one.
- **Deterministic:** same model + template + baseline → byte-identical recipe and run record;
  no timestamps anywhere in the family.
- **The receipt is the preflight anchor:** the implementor refuses to work unless
  `.packet/manifest.json` exists and the **provenance commit** it names is the root of history —
  `git rev-list --count HEAD` == 1 only at launch, `baseline + N commits on top` afterwards
  (ADR-049 invariant 3, #694). Exit 3 = tampering, exit 2 = sanctioned but uncommitted work,
  exit 0 = OK with the phase named.
- **The run record is the audit surface:** Gate-4 questions about implementor foreknowledge
  are answered by `packets/runs/…`, committed history in the real repo.
