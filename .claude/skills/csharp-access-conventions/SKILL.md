# C# ResourceAccess conventions

A **ResourceAccess (RA)** encapsulates *access to exactly one resource* (a relational DB, a document
DB, an API, a queue, …) and hides that resource's access-volatility behind its contract. It is the
**only** layer that touches the outside world.

## What an RA is — and is NOT

- **Is:** the boundary that reads/writes one resource and **transforms store entities ↔ contract
  DTOs**.
- **Is NOT:** a place for business logic, rules, validation, or orchestration — those live in Engines
  (logic) and Managers (orchestration). An RA whose `if` encodes a *business* rule is a smell; push it
  up.
- Talks **down** to its resource only. An RA never calls a Manager or an Engine, and never another RA.

## Shape (per ADR-022)

- Two projects: `Interface` (generated contract + DTOs) and `Service` (your code). You write **only
  the Service method bodies**; the dispatcher, DTOs, facets, and `.csproj` are generated — never edit
  `<auto-generated>` / `.g.cs` files.
- **Namespace ≡ folder path** — inherited from the generated Interface; just match it.

## Dispatch over operation variations

The facet operation is declared once over an abstract base request DTO; the generated dispatcher
`switch`es to your per-variation method (one per hierarchical-DTO variant type). You implement **one
method body per variation**. Unlike a Manager, an RA variation is **not** a use case — it is a
reusable resource operation called by *many* use cases. Organize by your own operations/DTOs, not by
use case. (SPVS `PKAccess.IArbeitnehmer.CreateSnapshot` switches `SnapshotMutation` /
`SnapshotNeuAnstellung` to per-variation methods.)

## Entity ↔ DTO at the boundary (hard rule)

- **Never leak a store entity past the contract.** EF entities, Mongo documents, and API wire types
  stay inside the RA; map them to/from the contract DTOs at the boundary.
- Map with **explicit code or a source-generated mapper (Mapperly)**. **Do not use AutoMapper**
  (runtime cost, silent drift, now commercial).

## The filter pattern (criteria → query)

Polymorphic `Filter` *criteria* DTOs compose a query — they do not multiply method names. Build the
query from the criteria fields, **parameterized** (never string-concatenate). The concrete query
mechanism is flavor-specific (LINQ→SQL, a Mongo filter, a query string) — see your flavor skill.

## Shared resource-plumbing

An RA's operations share plumbing — the connection/client, locking, id-generation, the entity↔DTO
mapper. Keep that in the component's **main Service file**; per-variation files (when large) reuse it.
This clustering is the RA's exception to "one file per variation": reuse lives *inside* the RA,
because the RA owns the resource.

## The resource seam: the one sanctioned catch in the system

Everywhere else in the system, business code writes `Result` and never `Errors`, and never catches
(ADR-022's amendment of 2026-08-23; ADR-061 decision 8). **This component is the exception** — the
single place a `catch` is sanctioned — and it has exactly four jobs:

> **classify · retry · answer what is answerable as data · rethrow what is not.**

An error is a **failure to answer**; "no" is an answer. `Response<T>` stays the wire shape, and its
error lane still has exactly one author — the iFX boundary net (#985), not you. So there is no
`ErrorInfo`, no `HasErrors`, no `GetResult()` and no `ResponseException` in an RA body either. What
is different here is the `catch`, not the envelope.

The per-flavor tables — which fault class is answered and which is rethrown, with the raw codes —
are carried by the flavor skills (csharp-access-relational-db / -document-db / -rest-api). Read
the table for your flavor before writing the seam.

### First: most "errors" are not faults at all

The largest category raises nothing, is never classified, and never enters the `catch`. It is an
ordinary return value:

| Situation | The store | You return |
|---|---|---|
| A read matched nothing | returns an empty set | an empty typed collection — an answer |
| A conditional update changed no row | returns `0` rows affected | `Applied = false` — an answer |
| A delete removed nothing | returns `0` | `RemovedCount = 0` — an answer |
| The store computed a refusal (the claim exceeds stock) | returns its verdict | the verdict field — an answer |
| A REST lookup answers `404` | returns a response (statuses do not throw) | `Found = false` — an answer |

**So prefer designing the fault away.** A verdict the store computes and returns beats a `CHECK`
violation caught at the seam; a conditional update returning `0` rows beats a concurrency exception.
The `CHECK` still belongs in the schema — as the invariant a driver bug cannot get past — but if it
*fires*, the code that wrote it was wrong: that is a rethrow, not an answer.

### The answerability test — all three, or rethrow

A **raised** fault becomes result data only when:

1. **The contract already asks the question** — a typed field carries the answer ("did the write take
   effect?", "what is the current version?"). No field means nothing to answer with. If the design
   *should* ask it, that is a `DESIGN GAP` on the protocol sheet, never an invented code.
2. **The design declares the mapping** — the Resource Protocol Sheet's **`faults:` section**
   (`resource-protocol/2` §5, #999 — one sheet per seam) names, per contract operation, the fault
   identity and the result
   field it answers into; the product fault taxonomy (ADR-048 §3) is where the raw product codes map
   onto that identity. Answerability is the resource-designer's call, reviewed at Contract; it is not
   yours to decide at the keyboard — and it is **checked**: `just resource-protocol-check` reds an
   Access whose filtered catch answers an identity none of its sheets declares — the check unions
   the declarations across every seam the Access stands on, because the scan is one `Service/`.
3. **The fault class means exactly one thing here** — a unique violation on a *dedup marker* means
   "this intent already ran". The same violation on an arbitrary write could be that or a key defect;
   ambiguous means not answerable.

**The default is rethrow.** Rethrow with a bare `throw;` so the stack survives, and rethrow the fault
**as it reached the seam boundary** — the seam's own product-free fault type (`StoreFault(identity)`),
never a raw `SqliteException` / `NpgsqlException` re-wrapped by you. In a host that opted into the
boundary net, the net logs it under the ambient W3C trace and answers the caller `UNEXPECTED` with
no internal detail (correlation is the trace both sides are already in, not a field); in-proc it
stays a live exception all the way up. Nothing above you catches it, which is the point.

### The shape: shared plumbing retries and rethrows, the operation answers

```csharp
// shared plumbing — one unit of work under the bounded budget. Classify, retry, rethrow.
private static async Task<Response<T>> Execute<T>(Func<T> unitOfWork) where T : class
{
    for (var attempt = 1; ; attempt++)
    {
        try { return ResponseBuilder.Build(unitOfWork()); }
        catch (Exception fault)
        {
            if (StoreFaultClassifier.Classify(fault) != StoreFaultKind.Transient || attempt >= MaxAttempts)
                throw;                        // a failure to answer — not yours to dress up
        }
        await Task.Delay(TransientBackoff).ConfigureAwait(false);
    }
}

// per-operation — the one declared answerable fault, answered into its declared field.
public Task<Response<SaveProfile_Result>> Save(SaveProfile request)
    => Execute(() =>
    {
        try
        {
            store.Replace(ToRow(request.Profile), request.ExpectedVersion);
            return new SaveProfile_Result { Applied = true };
        }
        catch (StoreFault f) when (f.Identity == "store:version-mismatch")   // sheet-declared
        {
            return new SaveProfile_Result { Applied = false, CurrentVersion = store.VersionOf(request.Profile.Id) };
        }
    });
```

Two rules the shape encodes:

- **The answering catch is per-operation and filtered** on one declared fault identity — because only
  the operation knows which field carries the answer. Never `catch (Exception)` to answer.
- **The retry-and-rethrow half is shared plumbing**, one wrapper for the whole component, so the
  budget is spent in one place and cannot be layered by accident.

`ResponseBuilder.Build(result)` is the only envelope call in your vocabulary. There is no
`Carrying(ErrorInfo)`.

### Raw detail belongs to telemetry, never to a contract

Nothing product-specific crosses your contract — not a SQLSTATE, not `SQLITE_BUSY`, not a driver
message, not a stack. Surfacing `40P01`/`23505` would re-leak the very storage technology this
component and the ADR-048 deployment split exist to hide, coupling every consumer to what is a
deployment concern ("Leaking implementation details into contracts"). Under this model that stays
true by construction: an answer is a **business field**, and a rethrow carries the seam's
**product-free** fault identity.

The raw fault is the **span's**: put `db.system` / `db.operation` / `error.type` / retry counts on the
RA span, correlated by the ambient W3C trace context (ADR-031). A caller correlates by trace id, not
by envelope payload.

### Reading the Comanda example

The Comanda golden-process Access components (in the theagent-unchained monorepo — not shipped
with this skill) show the classify-and-retry structure and the seam's `StoreFaultClassifier` —
copy those when you have that checkout. It still implements the **pre-amendment third hop**, answering
`Carrying<T>(…ResourceUnavailable)` and `Carrying<T>(…Conflict)` where these rules say rethrow;
migrating it was **deferred by the SA** (ADR-061 amendment, "the first application of this shape is
the next project"). Do not copy that half.

## Retry safety & idempotency (ADR-048 §2, corrected 2026-07-31 against the IDesign corpus)

Transient-fault retry is the RA's job in this project (access volatility) — **do not queue** RA
calls to make them async (the Method forbids queuing to Engines/Access; queuing is Manager-to-Manager
across subsystems only). The model is **at-least-once + idempotent receiver**, never exactly-once.

**A timeout is an unknown outcome, not a failure.** Retry silently converts *unknown* into
*assumed-failed* — that conversion is the bug. Retry is sound exactly when "unknown" and "failed"
are interchangeable, which is the definition of idempotent arrived at from the failure side.

### Preconditions — all four, before any key work

1. **Never layer retry.** RA 3× beneath a Manager 3× = 9 hits on a database that is already failing;
   cascading failure and thread-pool exhaustion follow. Decide the retry *level* once: if the RA
   retries, nothing above it may.
2. Retry **only genuinely transient faults** — never constraint violations, not-found, bad request.
3. **Backoff with jitter.** Immediate retry is a self-inflicted DoS.
4. **Bounded, with a plan for exhaustion — and the plan is `throw;`.** A store that has not answered
   after N attempts has not answered; that is the textbook failure to answer (ADR-061 decision 8's
   own example). Never spend the budget and then hand the caller a code meaning "it did not work".

### First rung — make the operation naturally idempotent

Before reaching for a key, try redesign: prefer `state = someValue` over `state += someValue`.
**Carry absolute state, not deltas** — most writes that "need" an idempotency key are delta-shaped
by accident, a lossy encoding of an idempotent fact. Check also whether the multi-write is really
one **atomic business verb** belonging in one RA (the canonical example verb is literally `Claim`):
if the steps are always performed in the same order atomically they belong in the RA under a
business-verb name; if the sequence can vary, the orchestration belongs above.

### If a key is genuinely needed

- The key must **identify the instance of intent**, be **minted upstream of the retry loop**, and be
  **resent unchanged** on every retry. A key minted *inside* the RA is useless — every retry mints a
  fresh one. Natural-vs-synthetic is **not** the question (that guidance belongs to weak references
  between schema sets, not to dedup); *"same intent, delivered twice"* is.
- **A duplicate is not "the same data" — it is the same intent delivered twice.** Payload equality
  and payload hashes cannot substitute: the distinguishing fact was never in the payload. Two
  identical restaurant rounds ten minutes apart are revenue, not a duplicate.
- **Marker and effect must share one commit** — same database, same transaction as the state change.
  A dedup store separate from the write target (a Redis cache in front of a SQL write) *is itself a
  distributed transaction*. Valid forms: a `UNIQUE` constraint inside the transaction, a conditional
  update / version-CAS, or actor turn-based concurrency.
- **Store the outcome, not just the key.** On a detected duplicate return the **original outcome**,
  not a generic OK — otherwise the caller silently loses its result (the new line id, the resulting
  stock level). This is the most commonly botched detail in real implementations.
- Where the key store lives is volatile: a **Utility called by the RA**, not business logic in the RA.

### Cross-resource atomicity

Not the RA's job. But the rule is **scope, not a ban on transactions**: a transaction lives under
one Manager operation (the Unit of Work) and never crosses a service / use-case / subsystem / cloud
boundary. If all resources are transactional and a coordinator is available, **one transaction is
the better answer** — sagas are what you do *in lieu of* it. Sagas and transactions mix: a saga step
may itself be a local ACID transaction. Reach for a saga when resources are genuinely separate or
non-transactional — and check first that the split isn't a decomposition failure in a costume.

When a saga *is* right, "do A, do B, retry 3×, compensate A on failure" inside the Manager is the
**fairy-tale-saga anti-pattern** — crash between B's failure and A's undo and nothing compensates.
Correct shape: saga framework in-proc to the Manager, steps driven by completion events over durable
messaging, **never parallel**, ordered most-likely-to-fail first, one resource per step.

**Compensation is a business problem, not a technical one** — it cannot be made generic, and it
often requires a *new use case*. Compensation paths belong in the business design with stakeholder
sign-off; an RA or Manager author must never invent them.

### Commands vs queries

You can reissue queries. You cannot assume commands against a third-party system are idempotent.
Going async does not remove the duplicate problem — at-least-once is the queue's advertised
contract. Ordering does not solve duplicates either.

## Route through the substitutable store seams — one per SLOT (ADR-048 §3/§4, ADR-065)

An Access stands on a list of named **slots**, one per resource in one role, declared in the
deployment view's slot table (`deployment-view/3`). Most Accesses have one; some have several —
a relational store the system owns beside the customer's ERP over REST is normal IDesign, because
an Access encapsulates a **volatility**, not a connection.

Each slot arrives as an **injectable seam interface** — the substitutable contract the
resource-designer defines (precedent: fixture `ITallyStore` constructor-injected into
`TallyAccess`). The RA constructor-injects one per slot, **in the slot table's order and under the
slot's name**; the real plumbing (entity, mapper, connection) lives behind each, flavor-specific.
The seams are what let the spec's resource **simulators** stand in to arm faults — do not `new` a
store inline or hide it behind a static. A seam is *shared* (the real Access consumes it, the
simulator implements it); it is **not** implementor-private.

The seam interface is a **type**, so two slots may legitimately use the same one — an invoice blob
store beside a photo blob store. What tells them apart is the slot name, which is why the
constructor parameter is named after the slot and not after the interface. Multiplicity of ONE role
(three shards, three tenants) is **one** slot with the instance chosen by key at call time, never
several: several would be identical fields where a typo compiles.

**You do not wire these.** The composition that constructs your slots is generated from the slot
table — production wiring the real drivers, spec wiring the simulators, same names, same order.
You receive them already constructed and connected.

## No component reads configuration (ADR-065)

Never. Not a connection string, not an endpoint, not a credential, not indirectly. Configuration is
resolved at the composition root and injected; the slot table names each slot's configuration
**key**, never its value. Your driver body *uses* its connection and receives it as a constructor
parameter — it never looks one up.

The line is **construction-time versus runtime**, which is why this does not contradict the IDesign
utility bar: values needed to *build* a component are injected, while cross-cutting services used
*during* a call — logging, security context, diagnostics — still go through the bar from any layer,
unchanged.

## Load your flavor skill — per slot

Read each slot's **`resourceKind`** and concrete **product** from the **deployment view**, not the
`.method` model (ADR-048 §1: technology binding is a deployment concern; the architecture stays
product-free). Load the matching skill **before** writing the body:

- `RelationalDB` → **csharp-access-relational-db**
- `DocumentDB` → **csharp-access-document-db**
- `RestApi` → **csharp-access-rest-api**
- anything else → stay on these base conventions + judgement, and flag the missing flavor.

The kind is a property of the **slot**, not of the Access, so an Access spanning two kinds answers
to two flavor skills — and therefore to **two answerable-fault tables**. They compose **per seam**:
each seam classifies, retries, answers and rethrows by its own kind's table, and each declares what
it answers on its own Resource Protocol Sheet. That is why sheets are keyed by the seam and not by
the Access (ADR-065 decision 4).

You should not be reading this having received two flavor skills at once. A packet carries one
flavor, and a mixed-kind Access is meant to arrive as one packet per slot; if you have been handed
two, stop and surface it (#1099) rather than picking.

## External inference (LLMs) — where it lives is a design choice (SA ruling 2026-08-24)

An LLM call has two legitimate homes, chosen per design — never a fixed placement:

- **A ResourceAccess**, when its answers carry business meaning. The contract speaks **business
  verbs** (`ClassifyComplaint`, `DraftReminder`), never "call the model"; provider, model choice
  and prompts are the encapsulated volatility. Wire-wise it is the RestApi flavor, and its seam
  classifies with the inference rows of the blessed fault tables (carried by the
  csharp-access-rest-api flavor skill): `429`/`5xx`/timeout →
  retry-then-rethrow; a **documented provider refusal** and **unparseable output after the seam's
  bounded repair** → **answerable as typed fields when the sheet declares them**; auth/quota →
  rethrow.
- **A Utility**, when the call is tier-neutral plumbing with identical semantics for every caller
  (embeddings for generic search, normalization). A Utility owns its own transport-level retries,
  like any utility; it answers no business question and declares no sheet.

**Retry ownership splits by NATURE, not tier.** *Fault* retry — the same question again because
the transport hiccupped: transient, bounded, invisible — is the seam's (or the utility's) plumbing,
and nothing above may layer on it (ADR-048 §2). *Answer-driven* retry — asking **differently**
because of what came back — is **business logic**: an Engine may loop on result data (the seam
already answered "no usable output" as a field, so no catch is involved), and it graduates to a
modeled Manager leg the moment the re-ask changes which downstream steps run.

## Smells (stop and fix)

- A store entity (EF/Mongo/API type) appears in a contract DTO or return → the boundary is leaking.
- Business rule / validation logic in the RA → belongs in an Engine or Manager.
- String-concatenated queries / manual escaping → use parameterized queries (SPVS's `EscapeSqlString`
  is the anti-pattern).
- AutoMapper → use explicit / Mapperly.
- Calling another RA, an Engine, or a Manager → wrong layer.
- `ErrorInfo`, `HasErrors`, `GetResult()`, `ResponseException`, or a `Carrying(...)`-style failed
  envelope → an answer is a typed field; anything else is the boundary net's lane.
- `catch (Exception)` used to *answer* → the answering catch is filtered on one declared fault
  identity; the broad catch belongs to the retry-and-rethrow plumbing only.
- Answering a fault class the sheet's `faults:` section does not declare → a **red check** (#999,
  ruled 2026-08-24); the fix is a design decision — surface it as a `DESIGN GAP` on the sheet,
  never an ad-hoc catch.
- Retrying a permanent fault (a constraint violation, a bad request) → no retry fixes it, and the
  budget is spent on a write that will never take.
- Catching to log and then continuing → the seam either answers or rethrows; there is no third
  outcome, and the raw detail belongs on the span.
