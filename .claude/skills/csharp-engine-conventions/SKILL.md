# C# Engine conventions

An **Engine** encapsulates an **activity** — a unit of business logic / computation (the *how* of a
rule or calculation). Engines are where the real domain logic lives.

## What an Engine is — and is NOT

- **Is:** stateless business logic. Input DTOs → compute → output DTOs. Deterministic where possible
  (same input → same output), which makes it trivially testable.
- **Is NOT:** an orchestrator (that's a Manager) and **NOT** a holder of external I/O. An Engine that
  opens a DB connection or calls an HTTP API is wrong — **wrap that resource in a ResourceAccess** and
  call the RA instead. ("A rules engine backed by a BRMS" = an Engine *plus* an RA to the BRMS.)

## Call direction (closed architecture)

- May call **down** to ResourceAccess (allowed — SPVS `ValidationEngine` calls `IArbeitnehmer.Editable`).
- **Never** calls another **Engine** (sideways is forbidden — each Engine encapsulates its full
  activity).
- **Never** calls a **Manager** (up is forbidden).

## Shape (per ADR-022)

- Two projects (Interface generated, Service hand-written); you write only the method bodies;
  `<auto-generated>` / `.g.cs` are off-limits; namespace ≡ folder path (inherited).
- **No flavors** — unlike Access, an Engine has a single convention set. (External dependencies belong
  in an RA, which carries the flavor.)

## Two engine shapes

- **Capability engine** — one operation, no variations, pure compute (SPVS `CalculationEngine.Calculate`).
  One file.
- **Per-variation engine** — the operation has request-DTO variations; the generated dispatcher
  `switch`es to per-variation methods (SPVS `ValidationEngine` has per-variation `Validate(...)`
  methods). One file per variation. A variation here is a reusable activity, **not** a use case.

## The error model: your verdict is result data, and you never catch

**An Engine writes `Result`, never `Errors`** (ADR-022's amendment of 2026-08-23, ADR-061 decision
8). `Response<T>` stays the wire shape on every contract, but its error lane has exactly one author
and it is not you: the iFX boundary net. There is no `ErrorInfo`, no `HasErrors`, no `GetResult()`,
no `ResponseException` and **no `try`/`catch`** anywhere in an Engine.

An error is a **failure to answer**. "No" is an answer — and answering "no" is most of what an Engine
does.

| Situation | What you do |
|---|---|
| The rule says no — not eligible, refused, rejected | a typed verdict field on the result DTO |
| A computation with a caveat — rounded, clamped, partial | a typed field carried beside the value |
| Nothing matched; the input set was empty | an empty typed result — that *is* the answer |
| An Access you called answered "not found" / "did not take effect" | read the field, apply your rule, answer |
| An Access you called **threw** | nothing — let it propagate |
| Your own precondition broken — a null the contract forbids, an unreachable `switch` arm, an overflow | **throw**; it is a bug, and a bug dressed as a verdict hides behind a green run |
| A value that will not parse or convert | use the total form (`TryParse`) — and treat a failure as a bug, because form-and-shape validation already ran at the edge |
| A required input the contract makes optional, with no rule for its absence | `DESIGN GAP` — do not invent a default |

**You have no resource seam, so you have no sanctioned catch.** The one `catch` in the whole system
is the ResourceAccess's resource seam, which classifies, retries, answers what is answerable as data
and rethrows what is not — that tier, not this one. Every catch an Engine reaches for is one of three
things: compensating for a bug (fix the bug), I/O that belongs in a ResourceAccess (move it), or an
answer the contract should carry as a field (add the field — in the design).

**A verdict is a field, and the Manager reads it.** Your caller does not inspect an error lane to
learn that a rule refused: it reads the field. Whether that field then *routes* the use case (the
sequence declares a leg and a guard reads it) or merely *rides through* to the result is the
Manager's design decision, visible in the declared paths — not something an Engine expresses by
choosing a return shape (ADR-061 decision 8).

**Answer-driven retry is yours; fault retry is not (SA ruling 2026-08-24).** Retry splits by
NATURE, not tier. Re-asking the *same* question because the transport hiccupped is the resource
seam's (or a utility's) plumbing — bounded, invisible, never yours to layer on. Asking
**differently** because of what came back is business logic, and an Engine **may loop on result
data**: the seam already answered "no usable output" / "did not take effect" as a typed field, so
your loop reads data and no catch is involved. The canonical case is external inference — retry
with the fallback prompt while the answer field says unusable. The loop **graduates to a modeled
Manager leg the moment the re-ask changes which downstream steps run** — then it is orchestration,
and it exists in the activity diagram or not at all (ADR-061).

**Where validation lives (ADR-061 decision 13).** Value validation — form and shape of a request —
is a **Utility applied consistently at the edge**, never an Engine. Business-state validation — what
the current situation dictates — is exactly what a **ValidationEngine** is: a modeled box whose
verdict comes back as result data, and the Manager's first gateway reads it like any other answer.

**The invariant behind the plumbing (ADR-022 amendment):** an in-flight `Response<T>` inside a
process never carries an error lane. In-proc, an unexpected failure is a live exception; across a
hosted boundary in a host that opted into the boundary net, the caller-side half rethrows before
the proxy returns (activation is a host-composition choice — SA ruling 2026-08-24); in a host that
did not opt in, nothing authors a lane in the first place. Either way a populated error lane never
reaches you, and inspecting one would be dead code.

The whole answer-vs-throw line follows one blessed set of fault tables: the rules above are its
Engine tier (Table D), and the Access tier you call into is carried by the C# Access flavor
skills (csharp-access-relational-db / -document-db / -rest-api).

## Smells (stop and fix)

- External I/O (DB / HTTP / file / queue) inside an Engine → move it to a ResourceAccess.
- Calling another Engine → fold the needed activity in, or reconsider the decomposition (escalate to
  the architect).
- Orchestration (sequencing several downstream calls to fulfil a use case) → that's a Manager's job.
- Hidden mutable state, or time/randomness that isn't passed in explicitly → breaks determinism and
  testability.
- `try`/`catch`, `ErrorInfo`, `HasErrors`, `GetResult()`, `ResponseException` anywhere in an Engine →
  a refusal is a typed field; a bug is a throw; there is nothing left for a catch to do.
- A refusal returned as an empty/default result with no field saying it was refused → the caller
  cannot tell "no" from "nothing"; give the verdict its own field.
- Catching an Access's exception to turn it into a verdict → that fault is a failure to answer, and
  the seam already decided; let it propagate.
