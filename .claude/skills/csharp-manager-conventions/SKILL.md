# C# Manager conventions

A **Manager** encapsulates a **use case's sequence** — it *orchestrates*, it does not compute. It is
the subsystem's entry point and the only component a Client calls per use case.

Since ADR-061 you do **not** write that sequence. The entry method is generated from the modeled
sequence and its declared paths — the activity diagram the Software Architect reviewed at the design
gates, compiled. Your surface is the half below it: the private step, guard and answer methods.

## What a Manager is — and is NOT

- **Is:** an orchestrator. Its entry body is the **use-case sequence**: one line per modeled box, in
  model order, plus the gateways the declared paths draw — all of it generated.
- **Is NOT:** a place for business logic (→ Engines) or resource access (→ ResourceAccess). A Manager
  doing a calculation or touching a DB is a smell.

## One use case, four files — two of them yours (ADR-022 §1, ADR-027, ADR-061)

A Manager operation is declared once over an abstract base request; the generated dispatcher
`switch`es to your per-variation use case, and **each variation IS a use case**. Managers are the
*only* component where a variation maps 1:1 to a use case. A variation whose use case only a
**parked** business process asks for (#1256) has no use case in this build: its arm is generated
as a `NotSupportedException` naming the process that revives it — never write a handler for it by
hand. Per use case, under its facet folder:

| File | Owner | Holds |
|---|---|---|
| `{Permutation}UseCase.g.cs` | **generated** | the entry method (the diagram), the constructor + `For(caller)` resolution, the plumbing (one `IFxActivity.Box` call per box, run-context writes, path record, envelope wrap), and the `partial` declaration of every method you implement |
| `{Permutation}Run.g.cs` | **generated** | the run context: the request, one slot per component-call box, the declared path taken |
| `{Permutation}UseCase.cs` | **yours** | the step / guard / answer implementations |
| `{Permutation}Run.cs` | **yours** | run-context slots the generator cannot infer |

**Never edit a `.g.cs` file** (its first line says `<auto-generated>`); it is re-emitted on every
model change and your edit is gone. If the entry body is wrong, the **model** is wrong: which
components a use case calls, in which order, and which decisions it takes are architecture, reviewed
on the diagram. Emit `DESIGN GAP: <what the diagram should say>` and stop — do not compensate in a
step method.

**Read the generated header first.** It carries the use case's description, the model's own Mermaid
activity graph, and each declared path's guard prose in the design's own words; each declaration you
implement carries the model's note on that box. That is your brief — you should not need the model
open beside it.

## What you write

Every method is **born throwing** `NotImplementedException` naming its box or path. Those throws are
your work queue; a fresh scaffold compiles, so the spec layer runs and reports RED rather than
failing to build.

**A component-call step** is handed its modeled callee as its **first parameter**, builds the request
DTO from the run context, calls the proxy on the contract's own signature, and returns that answer
**as-is**:

```csharp
private partial async Task<Response<Bookings.FetchEveningBookings_Result>> Step02_FetchEveningBookings(
    Bookings.IBookings bookings, ReleaseNoShow_TimerRun run)
    => await bookings.FetchEveningBookings(new Bookings.FetchEveningBookings { Date = run.Request.Date });
```

No unwrap vocabulary lives here — no `.Result` read on the returned envelope, no `GetResult()`, no
`ResponseBuilder`, no span code, no `try`/`catch`. The generated plumbing unwraps into the run slot.
Your half declares **no dependencies**: never a field, never `Proxy.ForComponent<…>`. A step can only
call the component the diagram handed it, which is the point.

**An internal step** is this Manager's own work — a box with no callee (the modeled example: *verify
the e-mail address*, right after a component call fetched the user). It takes only the run, has no
envelope, and hands its result forward through a slot you declare on `{Permutation}Run.cs`:

```csharp
private partial Task Step03_VerifyEmailAddress(AddToWaitlist_EveningRun run)
{
    run.EmailVerdict = EmailShape.Check(run.FetchAccount.Email);   // hand-owned slot
    return Task.CompletedTask;
}
```

**A guard** decides one modeled gateway from what the boxes already answered. It takes only the run,
is synchronous and pure — no calls, no I/O, no side effects — and its doc comment quotes the model's
own words for the path it selects:

```csharp
private partial bool NothingPastGrace(ReleaseNoShow_TimerRun run)
    => run.SelectExpiredHolds.ExpiredHolds.Count == 0;
```

**An answer method** assembles the result DTO for one declared path: `Result_<Path>(run)`. The
plumbing wraps it in the contract's envelope; you build the `_Result`, not the `Response<T>`.

## Dataflow: the run context, and what a slot really holds

Every step, guard and answer takes the run context and nothing else — which is why the entry body
carries no dataflow of its own. A generated slot holds the box's **unwrapped answer**, and its doc
comment says exactly what that means: **the box's LAST answer**. A box that runs per item leaves only
its final write there.

So a box that fans out keeps its aggregate in a **hand-owned slot** on `{Permutation}Run.cs` — and
every later guard and answer reads *that*, never the generated slot. Reading `run.UpdateBooking` as
"the release answer" when the box wrote N bookings is the predictable bug the doc comment forestalls.

## Fan-out lives inside its step method

A box executed per item loops **inside** its step method — the diagram draws one box, so the entry
body has one line. Accumulate into your hand-owned slot and return the last envelope for the box:

```csharp
private partial async Task<Response<Bookings.UpdateBooking_Result>> Step04_UpdateBooking(
    Bookings.IBookings bookings, ReleaseNoShow_TimerRun run)
{
    Response<Bookings.UpdateBooking_Result> last = null!;
    foreach (var hold in run.SelectExpiredHolds.ExpiredHolds)
    {
        last = await bookings.UpdateBooking(new Bookings.UpdateBooking { BookingId = hold.BookingId });
        run.Released.Add(last.Result);        // hand-owned aggregate; the guard reads this
    }
    return last;
}
```

The bare `.Result` read is safe **here and only here** by the ADR-022 invariant below: an in-flight
`Response<T>` inside a process never carries an error lane. Prefer one call carrying the whole set
where the contract offers it (the callee then decides, and an empty set is an empty call rather than
no call). If a per-item box can legitimately run **zero** times, that changes which steps run: it is
a branch the diagram must draw — `DESIGN GAP`, not a step-level invention.

## The error model: an error is a failure to answer; "no" is an answer (ADR-061 decision 8)

**Business code writes `Result`, never `Errors`.** Every answer the contract question can have —
"zero customers found", "not all dishes available", "the write did not take effect", a refusal, a
validation verdict — is a typed field on the result DTO. There is **no** `ErrorInfo`, no `HasErrors`,
no `GetResult()`, no `ResponseException`, no error short-circuit and no `try`/`catch` anywhere in a
Manager. `Response<T>` stays the wire shape on every contract; its error lane is not yours to author.

An answering field takes one of two shapes, and which one is a **design** decision you can read off
the diagram:

- a **routed outcome** — the sequence declares a leg, the generator emitted a gateway, and a guard
  method reads the field; or
- a **carried fact** — no branch, and the field rides through to whoever reads it. Your answer method
  copies it onto the result.

The same field may be routed in one use case and merely carried in another. If a downstream "no"
seems to need a branch the diagram does not draw, that is a `DESIGN GAP` — never an invented `if`.

**Errors are the unexpected only** — the store unreachable after the resource seam's own retries, and
bugs. They are exceptions, and business code never catches them. The **one** sanctioned catch in the
whole system is the **ResourceAccess's resource seam**, which classifies, retries, answers what is
answerable as data and rethrows what is not; it is not in this tier.

**The invariant that makes the plumbing's unwrap safe (ADR-022 amendment):** an in-flight
`Response<T>` inside a process never carries an error lane. In-proc, an unexpected failure is a live
exception — nobody authored the lane. Across a hosted boundary, the caller-side half of the iFX
boundary net rethrows before the proxy returns. So a populated error lane never reaches you, and
inspecting one would be dead code.

## Where validation lives (ADR-061 decision 13)

There is **no** implicit validation step, generated or hand-added, and no "the Manager is the
firewall" rule — that is not Method vocabulary.

- **Value validation** — form and shape of the request — is a **Utility applied consistently at the
  edge**. It is not a modeled box and not a Manager concern.
- **Business-state validation** — what the current situation dictates — is a **modeled
  ValidationEngine box**. Its verdict comes back as result data, and the first gateway of the
  sequence reads it like any other routed outcome.

If a use case needs validation the diagram does not draw, the diagram is what changes.

## Call direction

- Client → **one** Manager per use case. Manager → Engines and/or ResourceAccess (down).
- Manager → Manager **only asynchronously via a MessageBus** (queue / pub-sub) — **never** a
  synchronous sideways call.
- Reuse lives in the **Engines/Access you call**. A Manager use case is self-contained; there is no
  shared orchestration-helper layer.

## The nets that read the same model (ADR-061 decision 7)

Generation makes the diagram true by construction; verification did not retire.

- **IDESIGN031** (Roslyn, model-aware via the generated `.methodseq` manifest) — no extra and no
  missing downstream component call versus the sequence's steps. It now looks *through* your private
  step methods, so a foreign call smuggled into one is caught; it also asserts that the step method
  an internal box names exists. Its diagnostics are your to-do list.
- **`seqcheck trace`** (ADR-031 §§1–3) — the call recorder records a run's real call order and the
  differ scores it against the declared paths. A run is green only if its calls complete a path the
  design draws.
- **Granularity, stated with every number:** the differ gates **component-call** boxes. An internal
  box is declarable, observable (its span exists) and behaviourally covered by the spec layer's
  outcome assertions, but **not gated** — ingesting those spans is #986. Work mis-ordered inside a
  private method below a box is likewise below what these gates see.

**Write no tracing or span code at all** (`observability.md`). Each box's `idesign.activity_step`
scope is emitted by generated plumbing through one iFX primitive, which is also what makes the
generated body match the diagram box-for-box (ADR-061 decision 6) — nothing for you to annotate,
nothing to wrap.

## Where the older instrumentation mechanism stands

ADR-031 §4's compile-time span weaving into hand-written bodies was dropped as the day-to-day
mechanism (SA ruling 2026-08-14) and is **not** the convention here: under ADR-061 the box scope is
generated, so there is nothing to weave. It stays recorded, and Proposed, as the dormant fallback for
Manager bodies this generation does not reach — brownfield code under ADR-035, or code written before
the tooling landed. You never write, restore or look for it; ADR-031's amendment is the record.

## Smells (stop and fix)

- Editing a `.g.cs` file, or a `.g.cs` that disagrees with the diagram → the model changes, then
  regenerate; a wrong entry body is a `DESIGN GAP`.
- `ErrorInfo`, `HasErrors`, `GetResult()`, `ResponseException`, `try`/`catch`, or an `if` that
  short-circuits on failure, anywhere in a Manager → that outcome is result data; route it in the
  diagram or carry it on the result.
- A field, a constructor or `Proxy.ForComponent<…>` in your half → the callee arrives as the step's
  first parameter; anything else is a component the diagram does not hand you.
- Unwrapping in a step (`.Result`, `GetResult()`) outside a fan-out loop → return the proxy's answer
  as-is; the plumbing unwraps.
- A guard or answer reading a generated slot for a box that fans out → it holds the LAST answer; read
  your hand-owned aggregate.
- A guard that calls something, or decides on anything but what the boxes answered → a decision that
  changes which steps run belongs in the diagram.
- Business logic / calculation in a step method → move it to an Engine (a modeled box).
- Direct DB / HTTP / resource access → move it to a ResourceAccess.
- Synchronous Manager→Manager call → use an async MessageBus.
- An entry-validation call the diagram does not draw → value validation is the edge Utility's,
  business-state validation is a modeled ValidationEngine box.
